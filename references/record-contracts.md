# Record contracts

`.agile-flow/state.json` is the sole canonical plugin record. Generated Markdown under `.agile-flow/views/` is a projection, not an editable authority. The program writes backups, uses a same-directory temporary file followed by atomic replacement, locks cooperating writers, and validates schema, references, operation IDs, revisions, fingerprints, and the single-active-increment rule.

Active development means an open project with an open, unsuspended `in_progress` increment. Administrative closure preserves the development state but frees the active slot. Reopening unfinished work, including reopening a project that would reactivate it, checks current authorization and cannot create a second active increment; a suspended increment must separately `resume` after reopening.

Supported mutations are `initialize`, `update-project`, `update-backlog`, `complete-backlog`, `record-decision`, `rebind-authorization`, `prepare`, `start`, `mark-implemented`, `prepare-correction`, `record-evidence`, `record-review`, `record-blocker`, `resolve-blocker`, `record-improvement`, `follow-up-improvement`, `mark-delivery-change`, `pause`, `resume`, `close`, and `reopen`. `mark-delivery-change` creates a later delivery revision and preserves prior evidence. `prepare-correction` reopens the same increment after requested changes, a failed current-delivery check, or a documented defect under existing authorization. Name the basis and supporting evidence or defect source.

Manual state or generated-view edits stop mutation until reconciled. `reconcile-manual` requires the raw state hash, reviewer, and reason, preserves the edited file, then seals a structurally valid reviewed state. It cannot authenticate that review. Explicit `recover` verifies backup integrity under the lock and preserves each damaged snapshot; it never silently restores a backup. `inspect` compares recorded file hashes and reports stale evidence without mutating canonical state.

Within one delivery revision, the latest attempt for each required check establishes current verification; earlier attempts remain historical. A new review records the latest evidence IDs and covered-file fingerprints it evaluated. New checks or changed covered files cannot inherit an earlier acceptance. When a covered file changed, same-delivery `record-evidence` requires `change_impact: non_behavioral` and `impact_reason`; behavior-affecting changes require `mark-delivery-change` before fresh checks. The program validates this declaration but cannot determine semantic impact from bytes alone. Legacy reviews without evidence bindings remain readable and are conservatively pending when any same-delivery evidence is stale.
