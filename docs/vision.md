# Product Vision

**Product:** Adaptive development plugin for Codex, agile-flow.  
**Date:** September 20, 2026.  
**Status:** Documented shared vision.  
**Language update:** English throughout the plugin and its authored documents, as requested by the user on September 20, 2026.

## Vision

Help a person develop software with a Codex agent by turning needs into small, verifiable, useful deliveries, maintaining continuity across sessions and adapting direction based on learning.

The user directs the product; the agent carries out technical development within the agreed scope. Both share an explicit understanding of the objective, actual work status, and next step.

## Intended User and Problem

The plugin serves a person developing software with Codex, whether starting a new project or changing an existing repository.

It addresses context loss between conversations, scattered decisions, uncertainty about what is actually finished, and divergence between implementation and the original need. It also reduces user involvement in technical decisions the agent can resolve within its authorization.

## Value Proposition

Make collaboration with the agent a continuous, understandable development process: start from a need, select the next increment, implement it, verify the result, and use review to guide subsequent work.

Expected benefits:

- **Continuity:** Resume without reconstructing the project's context and decisions from scratch.
- **Shared direction:** Keep technical work connected to the problem and expected value.
- **Bounded autonomy:** Let the agent advance without repeated approvals within the agreed scope.
- **Verifiable results:** Distinguish implementation, technical verification, and user acceptance.
- **Adaptation:** Incorporate priority changes and learning without losing work traceability.

## Mission and Working Approach

Apply the book's adaptive management practices to collaboration between a person and an agent: shared vision, progressive planning, small deliveries, review, and continuous improvement.

The user defines objectives, priorities, and material product changes. The agent clarifies needs, investigates, proposes alternatives, plans technically, implements, and verifies. Its plan remains visible; it consults the user when a decision changes the expected outcome or exceeds existing authorization.

For new projects, start by understanding the problem, users, and constraints. For existing repositories, understand the requested change and inspect the relevant product state, with depth proportional to the work.

Both follow the same cycle:

**Understand → prioritize → prepare an increment → develop and verify → review with the user → adapt.**

Context, backlog, decisions, and evidence remain available across sessions. Product review evaluates the result; retrospection identifies concrete working improvements. Cadence adapts to the work without initially requiring fixed-duration sprints.

## Success Criteria

The product fulfills its vision when it enables the following:

1. Complete a delivery and review cycle in both a new project and an existing repository.
2. Resume in another session and identify the objective, current decisions, active work, blockers, pending reviews, and next step from records and repository state.
3. Link every increment to a need and observable acceptance criteria, presenting verification evidence and limitations.
4. Keep implementation, technical verification, and user acceptance separate without inventing approvals or results.
5. Resolve technical decisions within authorized scope without requesting previously granted permission again, and consult on decisions outside that scope.
6. Incorporate a priority change or review lesson into subsequent work while preserving the reason and previous work state.

## Boundaries

The product supports user-agent collaboration. It does not manage a human team or simulate agreements between fictional participants. The first version focuses on completing the development cycle and preserving its context.

This vision does not prescribe commands, architecture, storage formats, or integrations. Those decisions follow from what is necessary to fulfill its objectives.

## Language

All plugin-owned names, instructions, documentation, templates, generated records, and other authored material use English. User input can remain in the user's language. Existing product content, identifiers, external sources, and verbatim evidence retain their original form; English summaries provide context without altering provenance. Conversation with the user can follow the user's preferred language.

## Reviewing the Vision

Review this vision when the problem, intended users, or expected value changes, or when use shows that a premise needs adjustment. Changes must reflect decisions shared with the user.
