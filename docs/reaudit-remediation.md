# Re-audit remediation

Date: September 20, 2026. This record addresses the findings in `implementation-reaudit.md` without changing the approved vision, functional specification, or plugin design. The original audit and re-audit remain unchanged.

## Findings and corrections

| Finding | Correction | Executed regression evidence |
| --- | --- | --- |
| R01 — inconsistent current validity | `render` uses the same effective observation as `inspect` for current verification and acceptance. Increment views label differing stored states as historical and list stale evidence and changed paths. Summary views show effective states. Canonical state is not changed by rendering. | `test_r01_view_matches_effective_state_after_external_edit` changes a covered product file after passed checks and acceptance, then compares inspection and both generated views. The original implementation failed this test. |
| R02 — technical correction lifecycle | `prepare-correction` supports `technical_failure` with failed evidence from the current delivery, and `documented_defect` with a source and affected criterion or check. The earlier review-driven basis remains. The same increment moves to a new delivery revision and its current verification and acceptance reset. `start` still enforces the single-active-increment rule; current applicable authorization is required. | `test_r02_failed_check_reopens_same_increment_without_user_review`, `test_documented_defect_reopens_accepted_delivery`, and `test_full_replacement_technical_correction_and_review_cycle`. The original implementation rejected the first case. |
| R03 — review supersession | A new review may explicitly name an earlier same-delivery change request and the exact unresolved criterion parts in `supersedes`. `withdrawn` supports a pure withdrawal; `accepted` can accept the named parts. Unresolved changes on other parts remain outstanding, and all reviews and quotes remain in history. | `test_r03_explicit_review_supersession_is_scoped` and `test_withdrawal_restores_prior_acceptance_without_erasing_reviews`. The original implementation kept acceptance at `changes_requested` after an explicit superseding acceptance. |
| R04 — replacement authorization | `rebind-authorization` deliberately binds an existing increment to a different sourced user authorization that passes kind, revocation, supersession, and structured scope checks. History records the old and new references, reason, and supplied provenance. Correction and resume then use the new reference without recreating the increment. | `test_r04_replacement_authorization_resumes_and_corrects_same_increment`, `test_invalid_replacement_authorization_does_not_rebind`, `test_superseded_grant_can_be_replaced_before_resume`, and the integrated cycle. The original implementation had no rebinding operation. |

`prepare-correction` defaults to the existing review-driven basis for compatibility. Technical failures require identified failed evidence rather than an invented user request. Documented defects require an observed source and existing criterion or check; they do not create new authorized scope. Review supersession is explicit and confined to the same delivery revision. The program validates record structure and links, but cannot authenticate whether a supplied quote or source actually came from the user.

## Validation actually executed

- Before correction, four new R01–R04 regressions failed against the inspected implementation for the reported reasons. After correction, the full suite passed: **37 tests** (`python3 -m unittest discover -s tests -q`). The suite includes the integrated delivery revision 1 failure and user change request, replacement authorization, technical correction on the same increment, fresh verification, and explicit acceptance of revision 2. It also covers pause, replacement, and resume.
- The plugin validator passed. All six skill validators passed. The package tests extracted the distribution, resolved every skill reference from the installed layout, invoked the record program from another working directory, checked that the source PDF and product records are excluded, and checked preservation of existing marketplace entries. The re-audit documents are excluded from the distributable package.
- One real Codex scenario ran with `--ephemeral --ignore-user-config` and read-only sandboxing against an isolated temporary product. The agent followed the `status` skill, called `inspect`, reported no active work or authorization, and made no mutation; the canonical revision and fingerprint remained unchanged. The nested CLI initially could not initialize under the parent sandbox, then succeeded with a one-off execution escalation. It emitted model-cache compatibility warnings but exited successfully. No plugin was installed and no marketplace or Codex configuration was changed.

## Limits and remaining agent scenarios

The integrated correction/review cycle is deterministic record-program validation, not an end-to-end agent journey. Real-agent scenarios for existing-repository adoption, intent-based backlog selection, technical correction, scoped review supersession, replacement authorization, and final user acceptance remain unexecuted in this remediation. Acceptance in fixtures is explicit test input, not evidence of a real user's approval. Package and skill validators prove structure and reference resolution, not workflow quality in arbitrary conversations. Further live-agent evaluation should use isolated products and actual scoped prompts; it must not infer authorization or acceptance from this report.
