# TCH-0001 — Provide repeatable booking test fixtures

**Type:** TCH · **Status:** Draft proposal
**Order:** 4, proposed · **Estimate:** Not assigned; no repository assessment performed
**Target release:** v0.1.0 · **Iteration:** [ITER-001](../release/v0.1.0/iterations/ITER-001/sprint_planning.md), draft selection

## Need and value

Repeatable isolated test data makes conflict, retry and empty-calendar verification dependable without using real customer data.

## Scope

Include available, occupied and empty-calendar cases and a scoped reset procedure. Exclude production resets and live-data imports.

## Type-specific detail

Inspect existing repository tools before choosing a fixture mechanism. Identify the isolated environment explicitly and ensure reset operations cannot target unrelated data.

## Acceptance criteria

| ID | Condition | Observable result |
| --- | --- | --- |
| AC-01 | Fixture setup runs twice. | The same logical test cases are produced. |
| AC-02 | The dataset is reset. | Only the explicitly selected test data changes. |
| AC-03 | Another contributor follows setup instructions. | They can prepare the cases in a fresh test environment. |

## Definition of Done

| ID | Completion requirement | Required evidence |
| --- | --- | --- |
| DOD-01 | Exercise setup and reset in isolation. | Executed procedures and before/after observations. |
| DOD-02 | Verify unrelated-data preservation. | Boundary checks against a controlled unrelated test dataset. |
| DOD-03 | Document the usable setup and limits. | Instructions followed in a fresh environment and recorded outcome. |

These item-specific conditions are proposals. No requirement is verified, no work is done and no user acceptance exists in this fictional example.
