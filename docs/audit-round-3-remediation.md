# Audit round 3 remediation

Date: September 20, 2026. The approved vision, functional specification, and plugin design remain unchanged. `implementation-audit-round-3.md` is preserved as the original finding record. The R01–R04 corrections and their regressions remain in place.

## Corrections

| Finding | Reproduction before correction | Correction and evidence |
| --- | --- | --- |
| T01 — closed work retains the active slot | A temporary product started `INC-0001`, closed it unfinished, then could not start a second authorized increment. The new regression initially failed because inspection had no consistent `active_increment` and transition checks still counted the closed increment. | One active-development predicate now requires an open project, open increment, `in_progress` development, and no suspension. Validation, start, resume, inspection, and views use it. Closure preserves the development state but frees the slot. Reopening unfinished work or a project that would reactivate work checks current authorization; reopening cannot create a second active increment. The T01 regressions cover close, second start, rejected reopen, later successful reopen, conflicting resume, and superseded authorization on both increment and project reopen. |
| T02 — historical stale evidence blocks fresh acceptance | A temporary product passed its checks, accepted a delivery, changed a covered file, reran checks, and explicitly accepted the current same-delivery result. The new regression initially failed with effective acceptance stuck at `pending`. | Inspection now uses the latest attempt for each check as current verification while retaining older attempts. New reviews bind to latest evidence IDs and observed covered-file fingerprints. A later check or file change cannot inherit prior acceptance; an explicit current review can converge after same-delivery reassessment. Changed covered files require `change_impact: non_behavioral` and an `impact_reason` for a same-delivery rerun. Behavior-affecting changes require `mark-delivery-change` first. Tests cover fresh checks plus renewed review, historical retention, a rejected unclassified rerun, a behavior-change revision, and rejection of a behavior-affecting same-revision rerun. |

Inspection returns `active_increment`, `current_stale_evidence`, and per-evidence `current_attempt` alongside historical `stale_evidence`. Generated summary and increment views use the same effective states. The summary labels closed unfinished work as administratively closed and inactive; increment views distinguish stale current attempts from stale historical attempts.

## Compatibility and design boundaries

The canonical schema remains version 1 and existing records need no migration. New reviews add `evidence_ids` and `reviewed_fingerprints`. For older reviews without these fields, inspection reconstructs the evidence available at review time from durable operation history when possible. If that history cannot establish a binding, acceptance with recorded check evidence is conservatively pending rather than assumed current; the record is not discarded. A regression simulates an older review, confirms it remains readable, and confirms a later check cannot inherit its acceptance.

The program can detect changed covered bytes and validate the declared impact and source links. It cannot determine whether a change is semantically non-behavioral, authenticate a user quote, or detect changes to files that were never covered by recorded evidence. The agent must inspect the actual change and create a new delivery revision for behavior or relevant dependency changes. A passing check never creates user acceptance.

## Validation performed

- Before correction, the T01 regression failed at active-state inspection and the T02 same-delivery regression remained `pending` after a fresh explicit review. The separate behavior-revision path already passed. After correction, **45 tests passed** with `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -q`, including all retained R01–R04 regressions and new legacy-compatibility, replacement-authorization reopening, and no-inherited-acceptance tests.
- The plugin validator and all six skill validators passed. Package tests extracted the plugin, resolved skill references from the installed layout, invoked the program from another working directory, and checked marketplace-entry preservation. An independently generated package contained six skills and no source PDF, product records, or project audit/remediation reports.
- A real, ephemeral Codex `advance` run in an isolated product reproduced a failing unit test, corrected the same increment under an existing simulated fixture authorization, ran the test, recorded passed evidence on delivery revision 2, and left acceptance pending. A separate real `review` run used an explicit simulated test-user acceptance and bound `REV-0001` to current `EVD-0002`; inspection reported implemented/passed/accepted.
- In that same temporary product, a comment-only covered-file change made effective verification `not_run` and acceptance `pending`. A real `advance` run reran the unit check and recorded `EVD-0003` as a non-behavioral same-delivery reassessment. Verification became `passed` while acceptance stayed `pending`. A separate real `review` run recorded explicit test-user acceptance bound to `EVD-0003`; inspection and the generated increment view then both showed `passed` and `accepted`, with old stale evidence retained as historical.
- A separate real, ephemeral Codex close/advance scenario closed unfinished `INC-0001`, started authorized `INC-0002`, and observed the expected denial when reopening the first while the second was active. Inspection showed `INC-0001` closed, still `in_progress` historically, but not active; `INC-0002` was the sole active increment. No product code was edited in this scenario.

All agent scenarios used temporary fixtures, `--ephemeral --ignore-user-config`, and one-off nested-CLI execution permission. They did not install the plugin, publish anything, edit a marketplace, or change Codex configuration. Their authorizations and acceptance messages were explicit simulated test inputs, not real product approvals.

## Remaining limits

The behavior-affecting revision path, revoked-authorization reopening, and legacy-history edge cases have automated record coverage but were not each repeated as complete real-agent conversations. Existing-repository adoption, implicit skill activation, priority adaptation, blocker resolution, and learning follow-up also remain outside these round-three agent runs. Passing program tests, validators, and these isolated agent scenarios does not prove arbitrary future conversations will classify semantic impact or user acceptance correctly.
