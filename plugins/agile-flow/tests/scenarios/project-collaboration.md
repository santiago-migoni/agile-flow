# Project collaboration scenarios

Run in isolated temporary products. Never use a live product, installed cache or source checkout as writable evaluation data. Record actual responses, changed files and limitations separately from deterministic tests. Do not tell a forward-testing agent the expected answer before its attempt.

## Fixtures and acceptance rubric

| Scenario | Supplied context and request | Observable acceptance |
| --- | --- | --- |
| Close scope after an answer | User requested a release boundary, selected Odoo 19 dev, public repositories, same-server hosting and fresh explicit Deploy; now selects Community and asks to close the boundary. No release number is agreed. | Complete the reviewable outline; preserve scope and sourced approvals; propose numbering without assuming it; no iteration, implementation or request to ask for the outline again. |
| Integral assessment | User asks to review all pending matters and reduce bureaucracy. CLI details have a stale prerequisite before any planning; Rollback is included but restoration/data-loss behavior is unresolved. | Group actual pending matters, investigate authorized technical work, reconcile the source question and dependencies, and request only the consequential recovery choice. Do not fabricate a complete inventory from partial context. |
| Cross-domain continuation | A repair-booking app has one workshop, staff-created bookings, customer status, cancellations and email; payments/multiple workshops excluded. User settles fixed 30-minute slots and asks to finish scope. Same-day cancellation behavior remains unresolved. | Complete the same requested outline without importing Odoo terminology; distinguish capability inclusion from the remaining behavior choice; preserve the mandate and do not invent acceptance criteria as approved. |
| Partial correction | User removes mandatory staging but retains preproduction validation. | Supersede only the topology requirement, preserve validation, update dependent records and retain sources/history. |
| Authorized research | User delegated investigation of initialization within agreed scope; no product choice is pending. | Perform bounded research rather than ending with a promise. Label documentation evidence separately from operational verification. |
| Strategy correction | User returns from a technical discussion to the desired product outcome. | Stop technical drilling, consolidate the outcome and assign future questions a relevant resolution point. |
| Existing project instructions | User asks to adopt managed guidance in a product with custom AGENTS.md prose. Then request status and later update after manually changing the managed block. | Preview and preserve custom bytes; status makes no writes; update surfaces manual edits and does not force replacement. |
| Fresh discovery | Generate project guidance in a fixture and start a new Codex run at its root; repeat in a Git-rooted fixture with nested instructions and overrides. | Observe loaded instruction sources and effective precedence. Do not equate file generation or simulated adherence with automatic discovery. |

## Completion evidence

For release-boundary scenarios, inspect outcome, included capabilities, exclusions, success evidence, sourced decisions, and uncertainties with owners and resolution points. Check that updated questions no longer carry obsolete blockers and that proposals remain proposals. A successful record validator alone is insufficient.

For initialization, first initialize meaningful product context, then preview/apply instruction setup under that request. For existing projects, use the explicit adoption/update mandate. Preserve source and backup snapshots. Never claim that unexecuted scenarios passed.
